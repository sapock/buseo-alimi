# 부서 알리미 — 아키텍처·구현 계획 (v0.2)

> **v0.3 결정 (2026-11-19)**: merge-master 연동을 위해 **공유PC(Windows)에 배포**하기로 확정했어요(VM 안 씀). 2.1·2.3·9.2의 VM 관련 내용은 참고용으로만 남겨요. 구현 순서는 `docs/구현계획.md`를 따라요.

> v0.2: 1차 질문 답변을 반영했어요. 확정된 내용은 [10장](#10-확정된-결정-사항)에 모았고, 아직 `[가정]`으로 남은 부분은 기본값으로 진행해요.
>
> **규모**: 부서원 약 60명, 공지·Todo 월 10~15건 → 매우 작은 규모예요. SQLite 하나로 수십 년 치를 담을 수 있어요.

---

## 1. 한 줄 요약

**부서에서 항상 켜져 있는 PC나 사내 서버 한 대에 실행 파일 하나(웹 서버 + SQLite)를 띄우고, 부서원 모두는 브라우저로 접속해요.**
설치는 서버 한 곳에서만 하고, 부서원 PC에는 아무것도 설치하지 않아요.

## 2. 핵심 결정과 근거

### 2.1 개인 PC vs 서버 → **서버(상시 켜진 한 대) 방식 권장**

| 기준 | 개인 PC에서 실행 | 서버(상시 켜진 PC·VM)에서 실행 |
|---|---|---|
| 글쓴이가 여럿 | ✗ 각자 PC에 데이터가 흩어지거나, 한 사람 PC에 몰리면 그 사람이 PC를 끌 때 서비스도 멈춤 | ✓ 데이터가 한 곳에 모임 |
| 부서원 응답(Todo 완료) 수집 | ✗ 글쓴이 PC가 꺼져 있으면 응답을 받을 수 없음 | ✓ 언제든 응답 가능 |
| "한 눈에 보기" | ✗ 여러 PC의 데이터를 합쳐야 함 | ✓ 한 화면에서 전체 확인 |
| 마감 알림(향후 메신저·메일) | ✗ PC가 꺼지면 발송되지 않음 | ✓ 예약 발송 가능 |
| 배포·업데이트 | 사람마다 설치 | 한 곳만 교체 |

**결론**: 이 서비스는 "여러 명이 쓰고 모두가 보는 게시판"이라 **데이터가 한 곳에 모여야** 해요. merge-master가 결국 에이전트 PC(상시 켜진 PC)를 만든 이유와 같아요.

**배포 대상은 둘 중 무엇이든 같은 소스로 돌아가게 만들어요.** (공유PC와 리눅스 VM 둘 다 있음 — 확정)
- **A. 리눅스 VM (우선 권장)** — 서버로 관리되는 장비라 누가 끄거나 절전에 들어갈 걱정이 적어요. Linux 실행 파일 하나를 `systemd` 서비스로 등록해요(Docker도 선택 가능).
- **B. 공유PC (Windows)** — VM 조건(2.3)이 맞지 않을 때. 실행 파일 하나를 **Windows 서비스**로 등록해요. merge-master와 달리 Excel 자동화가 없어서 서비스로 등록할 수 있어요.

### 2.3 VM에 둘 수 있는지 확인할 것 (VM ↔ 공유PC 접근 포함)

VM에서 공유PC에 접근할 수 있는지는 **사내 망 구성(서브넷·방화벽·VLAN)에 따라 달라서** 소스나 설계만으로는 알 수 없어요. 아래 세 가지를 실제로 확인해야 해요.

| # | 확인 항목 | 왜 필요한가 | 확인 방법 |
|---|---|---|---|
| ① | **부서원 PC → VM** 접속 | 모든 부서원이 브라우저로 들어와야 함 | VM에서 `python3 -m http.server 8070` 실행 → 부서원 PC 브라우저로 `http://<VM IP>:8070` |
| ② | **VM이 부서원의 실제 IP를 보는지** | IP로 사용자를 식별하므로 **가장 중요**. 중간에 NAT·프록시·로드밸런서가 있으면 모든 요청이 같은 IP로 보여서 식별이 안 됨 | ①을 띄운 상태에서 접속하면 `http.server` 로그에 찍히는 IP가 그 PC의 IP와 같은지 확인 |
| ③ | **VM → 공유PC·부서원 PC** 접속 | merge-master 자동 등록(5.7)에만 필요. 에이전트는 공유PC `:8090`, 호스트 모드는 각 부서원 PC `:8080` | VM에서 `curl -m 3 http://<공유PC IP>:8090/api/sessions` (에이전트 실행 중일 때) |

**판단**
- ①·② 통과 → **VM에 배포**
- ③까지 통과 → merge-master 연동도 VM에서 함
- ①·②는 되는데 ③이 막힘 → VM에 배포하되 merge-master 연동만 포기하거나, 망 담당자에게 VM → 공유PC `8090` 허용 요청
- ① 또는 ②가 안 됨 → **공유PC에 배포** (같은 사무실 망이라 대부분 문제없음)

### 2.2 언어·프레임워크 → **Go(백엔드) + React·TypeScript(프론트) + SQLite**

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **Go + React + SQLite** | **실행 파일 하나**(프론트까지 `go:embed`로 포함)·런타임 설치 없음. Windows 서비스 등록이 쉬움. CGO 없는 SQLite 드라이버(`modernc.org/sqlite`)로 Windows 빌드가 간단. 빌드 빠름, 메모리 수십 MB | 프론트와 백엔드 언어가 다름 | **✅ 권장** |
| Rust(axum) + React + SQLite | merge-master와 같은 스택이라 코드·경험 재사용. 성능·안정성 최상 | CRUD 위주 앱에는 개발 속도가 느리고 학습 비용이 큼 | 대안 (merge-master 코드를 직접 가져다 쓸 계획이면) |
| Node/TypeScript(Hono·Fastify) + SQLite | 프론트·백엔드 한 언어, 타입 공유 쉬움 | 실행 파일 하나로 만들려면 Bun compile 등 추가 도구가 필요하고, 서버에 Node 설치가 필요할 수 있음 | 대안 |
| Python(FastAPI) | 빠른 개발 | 서버에 Python 런타임·패키지 설치 필요, 배포가 번거로움 | 비권장 |
| Tauri 데스크톱 앱 | merge-master와 같은 형태 | **이 서비스는 데스크톱 앱이 필요 없음**(모두 브라우저로 접속) | 비권장 |

**"가볍게"와 "배포 쉽게"** 두 요구에 가장 잘 맞는 것은 **실행 파일 하나 + DB 파일 하나** 구조이고, 이 구조는 Go로 만들 때 가장 손이 덜 가요.

**세부 라이브러리 (권장)**

| 영역 | 선택 | 이유 |
|---|---|---|
| HTTP 라우터 | `chi` (또는 Go 1.22+ 표준 `net/http` 라우팅) | 가볍고 표준 방식 |
| DB | SQLite (`modernc.org/sqlite`, WAL 모드) + `sqlc` 또는 직접 SQL | DB 서버가 따로 필요 없음. 부서 규모에 충분 |
| DB 마이그레이션 | `goose` 또는 내장 SQL 파일 | 실행할 때 자동 적용 → 업데이트는 exe만 교체 |
| HTML 소독 | `bluemonday` | 붙여넣은 메일 HTML의 스크립트 등 위험 요소 제거 (필수) |
| Markdown | 프론트 `markdown-it`(미리보기) + 서버 `goldmark`(저장 시 렌더) | |
| Excel 읽기 | `excelize` | 부서원 명단 업로드 |
| Windows 서비스 | `kardianos/service` | `alimi.exe install` 한 줄로 등록 |
| 실시간 갱신 | **SSE(Server-Sent Events)** | 서버→브라우저 한 방향 알림이면 충분. WebSocket보다 단순 |
| 프론트 | React + Vite + TypeScript, TanStack Query, React Router | |
| 에디터 | **TipTap**(ProseMirror 기반) — 서식 모드 / **CodeMirror** — 마크다운 모드 | 메일 붙여넣기·이미지 붙여넣기 지원 |
| UI | Tailwind CSS + 작은 컴포넌트 라이브러리(shadcn/ui 등) | 심플한 디자인 |
| 타입 공유 | OpenAPI 스펙 → TS 타입 생성(`oapi-codegen` + `openapi-typescript`) | merge-master의 ts-rs와 같은 목적 |

## 3. 전체 구조

```
┌──────────── 서버 (부서 공용 PC 또는 사내 서버) ────────────┐
│  alimi.exe  (Windows 서비스 / Docker)                      │
│   ├─ 웹 화면 (React 빌드 결과, exe에 내장)                  │
│   ├─ REST API  /api/*                                      │
│   ├─ SSE      /api/events   (새 글·응답 변경 알림)          │
│   ├─ 스케줄러  (마감 임박 점검, 자동 보관, 백업, merge-master 수집) │
│   ├─ 알림 발송 어댑터 (지금: 화면 알림 / 향후: 메신저·메일) │
│   └─ 데이터 폴더                                            │
│        ├─ alimi.db        (SQLite)                         │
│        ├─ uploads/        (붙여넣은 이미지)                 │
│        ├─ backups/        (매일 DB 사본, 보관 글 내보내기)   │
│        └─ alimi.toml      (설정)                            │
└────────────────────────────────────────────────────────────┘
             ▲  http://<서버IP>:8070
             │
   부서원 브라우저 (Chrome/Edge) — 설치 없음

             │ (선택, 4번 기능) 주기적으로 조회
             ▼
   merge-master 호스트 PC(:8080) / 에이전트 PC(:8090)  GET /api/sessions
```

**merge-master에서 가져온 설계 원칙**
- 실행 파일에 웹 화면을 포함해 **배포 파일은 하나만**(4장)
- **권한·검사는 서버에서** 판단(7장)
- **변경 기록** 남기기 → 누가 언제 무엇을 바꿨는지 추적
- 설정·데이터는 정해진 데이터 폴더 한 곳에 두기
- 개발 전용 기능과 가짜 의존성으로 테스트하기(13장)

**merge-master와 다르게 가져가는 부분 (가볍게 하려고)**
- 실시간 동시 편집이 없어서 **세션 액터·WebSocket이 필요 없어요.** 일반 REST + SQLite 트랜잭션으로 충분해요.
- 화면 갱신은 **SSE** 한 가지만 써요("새 글이 등록됐어요" 정도).

## 4. 사용자·권한

### 4.1 역할 (확정: 누구나 글쓰기)
| 역할 | 할 수 있는 일 |
|---|---|
| **관리자** (1~2명) | 부서원 명단 관리, 모든 글 수정·삭제, 설정·백업 |
| **부서원** (모두) | 글 등록, **자기 글** 수정·삭제·마감·완료 처리·응답 현황 보기, 대상인 글 보기, Todo 완료 응답, 내 대시보드 |

- 역할은 두 개뿐이에요. 관리자는 설정 파일(`admins = ["id1", "id2"]`) 또는 명단 엑셀의 `관리자` 열로 지정해요.
- 남의 글은 관리자만 고칠 수 있어요. 대신 글쓴이가 **공동 담당자**를 지정하면 그 사람도 고칠 수 있게 해요 `[가정]` (담당자가 휴가일 때 대비).

### 4.2 사람 식별 (확정: IP 우선, 없으면 ID 입력)
부서원 PC IP는 고정이고 명단 데이터를 신뢰한다는 전제예요. SSO는 쓰지 않아요.

1. 접속 IP가 명단에 있으면 → 그 사람으로 바로 들어와요(로그인 화면 없음).
2. 명단에 없는 IP면 → **"ID를 입력해 주세요"** 안내. 명단에 있는 ID면 바로 들어와요(관리자 승인 없음).
3. ID로 들어온 사람은 브라우저 쿠키(서명된 세션, 30일)로 기억해서 다시 묻지 않아요. 명단의 IP는 바꾸지 않아요(명단은 엑셀이 기준).
4. 같은 IP가 명단에 둘 이상이면 명단을 올릴 때 막아요(5.2).

**알고 쓰기**: 명단 밖 IP에서는 남의 ID를 입력해도 들어올 수 있어요. 공지·조사 요청 용도라 이 수준으로 충분하다고 판단했고, 모든 등록·수정·응답은 `audit_log`에 **IP와 함께** 남겨요. 관리자 화면에 "ID로 들어온 접속" 목록을 보여 줘서 이상한 접속을 확인할 수 있게 해요.

## 5. 기능 설계

### 5.1 글 등록 (요구사항 1)

**화면 흐름**: `+ 새 글` → 한 화면 안에서 아래 항목을 채우고 `등록`. 등록 전에 오른쪽에 **미리보기**를 보여 줘요.

| 항목 | 입력 방식 |
|---|---|
| 카테고리 | `공지` / `Todo` 두 버튼 중 하나 (기본: 공지) |
| 제목 | 한 줄 입력 (필수) |
| 마감일 | 달력 + 시각 (공지는 선택, **Todo는 필수** `[가정]`). 빠른 버튼: 오늘·내일·이번 주 금·다음 주 금 |
| 대상자 | `부서 전체` / `개인 선택` 토글. 개인 선택은 이름 검색 + 체크(여러 명) |
| 본문 형식 | `서식(HTML)` / `마크다운` 탭 |
| 본문 | 아래 5.1.1 참고 |
| 첨부 링크 | URL 목록 (선택) |
| 임시 저장 | 작성 중 내용을 브라우저에 자동 저장 → 실수로 창을 닫아도 복구 |

#### 5.1.1 본문 에디터
- **서식(HTML) 모드 — TipTap**
  - 사내 메일(Outlook)에서 본문을 복사해 붙이면 **표·굵게·색·링크가 유지**돼요.
  - 붙인 HTML은 저장할 때 **서버에서 소독**(bluemonday)해요. 스크립트·이벤트 속성·외부 iframe은 지워요. 표·인라인 스타일은 허용 목록으로 남겨요.
  - **이미지 붙여넣기**: 클립보드 이미지를 서버 `uploads/`에 올리고 그 주소로 바꿔 넣어요. 큰 이미지는 자동으로 줄여요(예: 긴 변 1600px).
- **마크다운 모드 — CodeMirror + 실시간 미리보기**
  - 이미지를 붙이면 업로드 뒤 `![](주소)`를 넣어 줘요.
- **저장 형식**: `body_format`(html|md), `body_source`(원문), `body_html`(서버가 렌더·소독한 결과). 화면에는 `body_html`만 보여 줘요.
- **링크**: URL을 붙이면 자동으로 링크가 되고, 새 탭으로 열려요.

> **⚠️ 위험 요소 (초기 시험 필요)**: Outlook 본문에 들어 있던 이미지는 복사할 때 `cid:`나 로컬 임시 파일 경로(`file:///...`)로 붙는 경우가 많아서 **브라우저가 읽지 못할 수 있어요.** 0단계에서 실제 사내 메일로 시험하고, 안 되면 "이미지는 따로 붙여넣어 주세요" 안내나 대체 방법을 정해요.

#### 5.1.2 수정·삭제
- 글 상세 화면 오른쪽 위 `⋯` 메뉴: 수정 / 마감일 변경 / 대상자 변경 / 완료 처리 / 삭제
- **마감일 변경**은 상세 화면에서 바로(인라인) 바꿔요. 바꾸면 변경 기록에 남고 대상자 화면에 `마감 변경됨` 표시가 떠요.
- **삭제**는 휴지통으로 옮겨요(30일 뒤 영구 삭제). 실수로 지워도 되살릴 수 있어요.
- 이미 응답이 있는 Todo를 크게 고치면 "응답한 N명에게 변경을 알릴까요?"를 물어요(향후 메신저 연동).

### 5.2 부서원 정보 관리 (요구사항 1-4)
- **엑셀 업로드**: `이름 / id / IP` 열. id가 키예요.
  - 올리면 바로 반영하지 않고 **변경 미리보기**를 보여 줘요: `추가 3명 · 변경 2명(IP 바뀜) · 명단에서 빠진 1명`.
  - 빠진 사람은 삭제하지 않고 **비활성**으로 바꿔요(과거 글·응답 기록 유지).
  - 같은 IP가 두 사람에게 있거나 id가 겹치면 그 줄을 빨갛게 표시하고 반영하지 않아요.
- **직접 입력**: 표에서 바로 추가·수정·비활성.
- **양식 내려받기**: 빈 엑셀 양식을 내려받을 수 있어요.
- `[가정]` 팀·파트 같은 그룹이 있으면 대상자를 "파트 단위"로도 고를 수 있게 열을 하나 더 받아요(질문 Q5).

### 5.3 목록·정렬 (요구사항 2)
- **기본 화면 = "내 할 일"**: 나를 대상으로 한 글 중 확인하지 않은 공지와 완료하지 않은 Todo를 **마감 임박 순**으로 보여 줘요.
- 정렬: `마감 임박순`(기본) / `등록일 최신순` / `등록일 오래된순` / `최근 수정순`
- 필터 칩: `전체 · 공지 · Todo` | `미확인·미완료만` | `마감 지남` | `내가 쓴 글` | 글쓴이 | 기간
- 검색: 제목·본문 (SQLite FTS5 전문 검색)
- 목록 한 줄: `[Todo] 제목 · D-2 (빨강/주황/회색) · 글쓴이 · 완료 12/30`
- 마감 지난 미완료 글은 맨 위에 빨간 띠로 따로 보여 줘요.

### 5.4 대시보드 (요구사항 3)

**부서원 시점 (나)**
- 카드: `미완료 Todo N` · `마감 지남 N` · `이번 주 마감 N` · `새 공지 N`(브라우저 기준)
- 이번 주 마감 달력(작은 타임라인)

**글쓴이·관리자 시점**
- 카테고리별 현황: 진행 중인 공지 N / Todo N, 이번 주 마감 N
- **Todo별 응답 현황** 표: 제목 · 마감 · 응답률 막대 · `완료 18 / 미응답 12`
- Todo 상세 → **완료자 / 미응답자** 두 칸으로 나눠 보기
  - 미응답자 `이름 복사` 단추(merge-master의 '접속 기록 없는 N명 이름 복사'처럼 → 메신저에 바로 붙여넣기)
  - 향후: `미응답자에게 메신저로 알림` 단추 (8장)
  - `엑셀로 내보내기`(응답 현황)
- 공지는 **확인 기록을 남기지 않아요**(확정). 대시보드에는 진행 중인 공지 수와 목록만 보여요.

### 5.5 응답 (Todo만)
- Todo 상세 아래에 큰 단추 하나: `완료했어요`
- 완료할 때 짧은 메모(선택)를 남길 수 있어요. 예: "공유폴더에 올렸습니다"
- 실수했을 때 `완료 취소`도 돼요(글이 '완료' 상태가 되기 전까지 `[가정]`).
- 응답할 때마다 SSE로 글쓴이 대시보드가 바로 갱신돼요.
- 공지는 응답이 없어요. 다만 **"새 글" 표시**는 브라우저에 마지막으로 본 시각만 기억해서 보여 줘요(서버에 기록하지 않아 가벼워요).

### 5.5.1 대상자 계산 (확정: '부서 전체'는 나중에 들어온 사람도 포함)
- `부서 전체` 글의 대상자는 저장하지 않고 **볼 때마다 지금의 활성 부서원**으로 계산해요. 명단에 새 사람이 들어오면 진행 중인 전체 대상 Todo에 바로 미응답으로 잡혀요.
- `개인 선택` 글만 `post_targets`에 대상자를 저장해요.
- 응답률 분모 = 지금 대상자 중 **활성** 부서원. 명단에서 빠진(비활성) 사람은 분모와 미응답 목록에서 빠지지만, 이미 한 응답 기록은 남아요.
- `[가정]` 글이 '완료' 상태가 된 뒤에는 대상자를 그 시점으로 **고정**해요(보관 JSON에 그 시점 명단이 들어가요). 끝난 조사의 응답률이 나중에 바뀌지 않게요.

### 5.6 완료·보관·백업 (요구사항 6)

**글 상태**
```
진행 중 ──(마감 지남 / 모두 완료 / 글쓴이가 '완료 처리')──▶ 완료 ──(N일 뒤 자동 또는 수동)──▶ 보관
```
- **보관함**: 보관된 글은 목록에서 빠지고 `보관함` 메뉴에서 읽기 전용으로 검색·열람해요(DB에도 그대로 남아요).

**별도 파일 백업 (확정: 가장 가벼운 방식 → 글마다 폴더 하나 + JSON)**

글이 '완료' 상태가 되는 순간 자동으로 아래 파일을 써요. 손으로 다시 쓰기도 할 수 있어요(`⋯` → `백업 파일 다시 쓰기`).
```
<백업 폴더>/2026/11/0042_4분기-예산-조사서/
    post.json        ← 글 전체 (아래 형식)
    img_01.png       ← 본문에 붙인 이미지 (있을 때만)
    img_02.jpg
```
```json
{
  "format": "buseo-alimi/post", "version": 1,
  "id": 42, "category": "todo", "title": "4분기 예산 조사서 제출",
  "author": {"id": "jhpark", "name": "박지훈"},
  "createdAt": "2026-11-02T09:10:00+09:00", "dueAt": "2026-11-20T18:00:00+09:00",
  "doneAt": "2026-11-21T00:00:00+09:00",
  "target": "all",
  "body": {"format": "html", "source": "...", "html": "... <img src=\"img_01.png\"> ..."},
  "links": [{"label": "양식", "url": "http://..."}],
  "responses": [{"id": "sylee", "name": "이서연", "done": true, "at": "...", "memo": "공유폴더 업로드"}],
  "notResponded": [{"id": "mskim", "name": "김민수"}],
  "history": [{"at": "...", "by": "jhpark", "action": "due_changed", "from": "...", "to": "..."}]
}
```
- **왜 이 방식인가**: 추가 라이브러리·압축이 필요 없고, 메모장으로도 열리고, 글 하나를 지우거나 옮기기도 쉬워요. 이미지는 base64로 JSON에 넣지 않고 파일로 두어서 JSON이 작아요. 본문의 이미지 주소는 같은 폴더의 상대 경로로 바꿔 써서, 폴더째 옮겨도 이미지가 따라가요.
- **쓰는 방법**: 임시 파일에 다 쓴 뒤 이름을 바꿔 넣어요(쓰다 끊겨도 반쯤 쓴 파일이 남지 않음 — merge-master의 `result.mmsave` 방식).
- **백업 폴더**: 기본은 데이터 폴더 아래 `archive/`. 설정에서 NAS·공유 드라이브 경로로 바꿀 수 있어요(VM이면 마운트한 경로).
- **되살리기**: 관리자 화면에서 `post.json`을 올리면 그 글을 다시 만들어요(DB가 사라졌을 때 대비).
- **DB 안전망**: 이와 별도로 매일 새벽 `VACUUM INTO`로 DB 파일 사본 하나(`backups/alimi-YYYYMMDD.db`, 최근 14개)를 남겨요. 파일 하나 복사라 가볍고, 진행 중인 글까지 보호해요.

### 5.7 merge-master 자동 등록 (요구사항 4) — **가능함, 제한 있음**

merge-master 소스를 확인해 보니, 참여자 서버가 **인증 없이 업무 목록 API를 제공**해요.

```
GET http://<호스트PC>:8080/api/sessions      (호스트 PC에서 공유 중일 때)
GET http://<에이전트PC>:8090/api/sessions    (에이전트 PC에서 서비스 중일 때)

→ [{ slug, title, requester, description, deadline, readOnly, closed, online, mine }]
```
(`crates/collect-server/src/hub.rs` `SessionListItem`, `lib.rs`의 `/api/sessions` 라우트)

**구현 방식**
1. **조회할 주소 목록**: 설정에 등록한 에이전트 PC 주소 + (선택) **부서원 명단의 IP 전체**를 `:8080`으로 조회해요. merge-master는 호스트가 각자 PC에서 띄우므로, 명단 IP를 훑으면 부서원이 띄운 취합을 찾을 수 있어요.
2. 스케줄러가 5분마다 조회해요(주소마다 1초 타임아웃, 동시에 10개씩). 응답이 없는 주소는 건너뛰어요.
3. 아직 없는 업무면 **Todo 글로 자동 등록**해요.
   - 제목: `[엑셀 취합] {title}` / 본문: `description` + **취합 주소 링크**(`http://<주소>/<slug>`)
   - 마감: `deadline` / 글쓴이: `requester` 이름과 같은 부서원 (없으면 '시스템')
   - 중복 판단 키: `주소 + slug + job id`(`GET /api/session?s=<slug>`의 `job`)
   - `closed`가 되면 그 글을 '완료'로 바꿔요.
4. 자동 등록한 글은 `merge-master` 표시가 붙고, 글쓴이가 대상자·본문을 고칠 수 있어요.

**제한**
- merge-master는 **공유 중(서비스 중)일 때만** 목록에 나와요. 호스트가 공유를 멈추면 보이지 않아요.
- 공개 API에는 **누가 대상자인지, 누가 다 입력했는지가 없어요.** 그래서 대상자는 `부서 전체`로 등록하고, 완료 여부는 부서원이 직접 `완료했어요`를 눌러야 해요.
  → 필수 입력 진행률까지 자동으로 맞추려면 **merge-master 쪽에 API를 하나 추가**해야 해요(질문 Q9).
- 명단 IP 전체를 주기적으로 훑는 것이 사내 보안 정책(포트 스캔 탐지)에 걸릴 수 있어요 → 처음에는 **에이전트 PC 주소만 등록하는 방식**을 권장하고, IP 훑기는 설정으로 켜게 해요.

**판단**: 1차 범위에는 넣지 않고 **6단계(선택)**로 둬요. 기본 기능이 자리 잡은 뒤 붙여도 다른 부분을 고칠 필요가 없어요.

#### 5.7.1 merge-master 개발자에게 보낼 요청안 (확정: 직접 수정은 못 하고 요청 가능)

지금 API만으로도 자동 등록은 돼요. 아래를 요청하면 **사람별 완료 여부까지 자동**으로 맞출 수 있어요. 요청은 우선순위 순이에요.

> **요청 1 (꼭 필요) — 업무별 참여자 진행 현황 조회 API**
> ```
> GET /api/sessions/{slug}/progress
> → {
>     "job": "업무 id", "title": "...", "deadline": "...", "closed": false,
>     "people": [
>       {"name": "이서연", "ip": "10.1.2.31", "filled": 12, "required": 12, "lastSeenMs": 1763...},
>       {"name": "김민수", "ip": "10.1.2.40", "filled": 3,  "required": 12, "lastSeenMs": null}
>     ]
>   }
> ```
> - merge-master는 이미 1c 접속자 표에 '필수 진행률'과 '마지막 접속'을 계산하고 있어서, 그 값을 JSON으로 내보내기만 하면 돼요.
> - `ip`는 이름이 같은 사람을 구분하는 데 써요(부서 알리미는 IP로 사람을 찾음). 넣기 어렵다면 이름만이라도 괜찮아요.
> - 이름과 진행률이 인증 없이 사내망에 보이게 되므로, **읽기 전용 토큰**(예: 호스트가 설정에서 켜는 `?key=`)을 두는 방식도 함께 제안해요.
>
> **요청 2 (있으면 좋음)** — `GET /api/sessions` 결과에 `job`(업무 id)과 `deadlineAt`(유닉스 ms)을 넣어 주세요. 지금은 업무마다 `/api/session?s=`를 한 번 더 불러야 하고, `deadline`은 시간대 없는 문자열이라 해석이 모호해요.
>
> **요청 3 (선택)** — 업무를 공유 시작·종료할 때 지정한 URL로 알려 주는 웹훅. 있으면 부서 알리미가 주기적으로 조회하지 않아도 돼요.

- 요청 1이 반영되면: `required > 0 && filled >= required`인 사람을 부서 알리미에서 '완료'로 자동 표시해요(부서원이 직접 누른 완료와 구분해 `자동` 표시). 대상자도 `people` 목록으로 정할 수 있어요.
- 반영되기 전에는: 대상자는 `부서 전체`, 완료는 각자 누르는 방식으로 동작해요.

```sql
members        (id TEXT PK, name, ip UNIQUE NULL, is_admin BOOL,
                group_name NULL, active BOOL, created_at, updated_at)

posts          (id INTEGER PK, category [notice|todo], title,
                body_format [html|md], body_source, body_html,
                author_id → members, due_at NULL,
                target_type [all|selected],
                status [open|done|archived|trashed],

post_editors   (post_id, member_id)            -- 공동 담당자
post_links     (post_id, url, label)
attachments    (id, post_id NULL, path, mime, size, created_by, created_at)

responses      (post_id, member_id, memo NULL, by [self|merge_master],
                responded_at, PRIMARY KEY(post_id, member_id))   -- Todo 완료만

audit_log      (id, at, actor_id, action, target_type, target_id, detail_json)

posts_fts      (FTS5: title, body_text)                     -- 검색
```

`부서 전체` 대상은 진행 중에는 지금의 활성 부서원으로 계산하고, 완료될 때 `post_targets`에 고정해요(5.5.1).

## 8. 향후 확장: 메신저·메일 발송 (참고 2)

지금부터 **발송 대기열(아웃박스) + 어댑터** 구조로 만들어 두면, 나중에 API만 끼우면 돼요.

```go
type Notifier interface {
    Channel() string                       // "web", "messenger", "mail"
    Send(ctx context.Context, n Notification) error
}
```
- 1차: `web` 어댑터만 — 화면 상단 알림 종, 탭이 열려 있으면 브라우저 알림(Notification API)
- 이후: `messenger`, `mail` 어댑터 추가 → 설정에서 켜고 끄기
- 발송 시점은 스케줄러가 정해요: **새 글 등록 시 / 마감 D-1 / 마감 당일 오전 / 마감 지남**
- 실패하면 재시도하고 `notifications.status`에 남겨요(merge-master의 '저장 실패 → 재시도 3번' 패턴).
- 대시보드의 `미응답자에게 알림` 단추도 이 대기열에 넣기만 하면 돼요.

## 9. 배포 설계 ("배포가 쉬워야 한다")

### 9.1 Windows 공유PC (VM이 안 될 때)
```text
alimi.exe            ← 파일 하나
alimi.toml           ← 처음 실행할 때 자동 생성 (포트, 데이터 폴더, 백업 폴더)
```
```bash
alimi.exe install     # Windows 서비스로 등록 + 시작 (관리자 권한 필요)
alimi.exe uninstall
alimi.exe run         # 서비스 없이 바로 실행 (시험용)
alimi.exe backup      # 즉시 백업
```
- 처음 실행하면 **관리자 지정 화면**이 떠요(그 PC에서 접속한 사람 = 첫 관리자, 또는 설정의 관리자 ID).
- 데이터 폴더: `C:\ProgramData\BuseoAlimi\` (서비스 계정이 쓸 수 있는 곳)
- 방화벽: `install`할 때 인바운드 규칙을 추가해요(`netsh advfirewall`). 회사 정책상 막혀 있으면 안내문을 보여 줘요.
- **업데이트**: 서비스 중지 → `alimi.exe` 교체 → 시작. DB 마이그레이션은 시작할 때 자동이고, 적용 전에 DB 백업을 먼저 떠요.
- 상시 켜 두기: 절전 해제 안내(서비스가 절전을 막는 기능도 넣을 수 있어요).

### 9.2 리눅스 VM (우선 권장 — 2.3 확인 통과 시)
```bash
sudo ./alimi install     # systemd 서비스 등록 + 시작 (/etc/systemd/system/buseo-alimi.service)
sudo ./alimi uninstall
./alimi run              # 바로 실행 (시험용)
```
- 데이터 폴더: `/var/lib/buseo-alimi/`, 설정: `/etc/buseo-alimi/alimi.toml`
- 방화벽: `firewalld`/`ufw`에서 포트(기본 8070) 허용 안내를 `install`이 출력해요.
- **IP 식별 주의**: VM 앞에 리버스 프록시(nginx 등)를 두면 접속 IP가 프록시 IP로 바뀌어요. 프록시 없이 직접 받거나, 둔다면 설정 `trusted_proxies`에 프록시 IP를 넣어 `X-Forwarded-For`를 읽게 해요(신뢰한 프록시에서 온 값만 읽음).
- Docker를 쓰고 싶으면 `Dockerfile`도 제공해요 → `docker run --network host -v /var/lib/buseo-alimi:/data buseo-alimi` (`--network host`여야 실제 접속 IP가 보여요).
- 업데이트: `systemctl stop` → 파일 교체 → `systemctl start` (마이그레이션 전 DB 자동 백업).

### 9.3 빌드·릴리스
- GitHub Actions(또는 사내 CI)에서 태그를 달면 `alimi.exe` + `SHA256SUMS.txt`를 만들어요(merge-master와 같은 방식).

## 11. 단계별 구현 계획

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **0. 골격·검증** | **VM 망 확인(2.3 ①②③)**, Go 서버 + React 빌드를 실행 파일 하나로 묶기(Linux·Windows), systemd/Windows 서비스 등록, SQLite 마이그레이션, **Outlook 본문 붙여넣기 시험**(Q12) | VM(또는 공유PC)에 `install` 후 부서원 PC 브라우저로 접속되고 **실제 IP가 보임**, 메일 붙여넣기 결과 확인 |
| **1. 사람** | 부서원 명단(엑셀 업로드 미리보기·직접 입력), IP 식별 → 없으면 ID 입력, 관리자 지정 | 명단 올리고 각 PC에서 자기 이름으로 들어옴 |
| **2. 글 (MVP 핵심)** | 등록·수정·삭제(휴지통), 카테고리·마감·대상자, 서식/마크다운 에디터, 이미지 업로드, HTML 소독, 변경 기록 | 메일 본문을 붙여 글을 올리고 대상자만 보임 |
| **3. 목록·응답** | 내 할 일, 정렬·필터·검색(FTS5), 확인·완료 응답, D-day 표시, SSE 갱신 | 응답하면 글쓴이 화면에 바로 반영 |
| **4. 대시보드** | 내 현황 카드, Todo별 응답률, 완료/미응답자, 이름 복사, 엑셀 내보내기 | 요구사항 3 충족 |
| **5. 보관·백업** | 완료→보관 흐름, 보관함, 글마다 `post.json` + 이미지 백업, JSON 되살리기, 매일 DB 사본 | 요구사항 6 충족 → **1차 배포** |
| 6. merge-master 연동 (선택) | `/api/sessions` 수집기, 자동 등록·마감 반영. 요청 1이 반영되면 사람별 완료 자동 표시 | 요구사항 4 |
| 7. 알림 발송 | 아웃박스 + 메신저·메일 어댑터, 마감 리마인드 | 참고 2 |

1~5단계가 MVP예요. 6·7단계는 앞 단계를 고치지 않고 붙일 수 있게 0단계부터 구조를 잡아 둬요(스케줄러, 아웃박스 테이블, `source` 열).

## 13. 테스트·품질

- Go 단위 테스트: 권한 검사, 명단 가져오기 비교(추가·변경·빠짐), HTML 소독(스크립트 제거·표 유지), 상태 전이, 마감 계산
- API 통합 테스트: 임시 SQLite로 서버를 띄워 등록→응답→대시보드 집계 확인
- E2E(Playwright): 여러 사용자(IP를 헤더로 흉내 내는 **개발 전용** 옵션)로 등록·응답·대시보드 흐름
- 가짜 merge-master 서버로 수집기 테스트
- 마이그레이션 테스트: 이전 버전 DB → 새 버전 시작 → 데이터 유지
